# MVP 用户流程

状态：阶段 0 已通过；阶段 2 对 Baseline 流程补充

## 1. 交互约定

用户通过 Codex 对话发起任务，通过 Workbench HTML 查看完整结果。

每个写操作必须形成一个可追踪的 Run。长流程失败后应能从已完成步骤恢复，不要求用户重新上传已保存的文件。

HTML 不保存业务状态。用户的选择、反馈、批准和版本必须写入 `.xhs-agent/` 中的结构化文件。

## 2. 首次建立博主 Baseline

### 典型请求

> 分析我的小红书账号，主页是……，采集 50 条。

### 流程

1. 识别任务为“建立或更新本人 Baseline”。
2. 检查 TikHub 配置和环境能力。
3. 确认主页、采集数量和评论范围。
4. 采集公开账号信息、笔记、互动和评论。
5. 保存标准化 Evidence 和采集质量报告，不落盘 API 原始响应。
6. 生成确定性数据底稿和质量闸门。
7. 质量通过后，由 AI 按三层画像与商业画像协议生成结构化 Candidate。
8. 校验 Evidence、反证、最低跨笔记数量、认识状态和置信度上限。
9. 保存 `pending_confirmation` Baseline 新版本。
10. 重建博主 Workbench 页面，等待助理或本人确认。

Workbench 中的搜索、证据折叠和打印只影响阅读体验，不修改 Baseline。用户通过 Codex 对话提交确认或修订意见。

### 用户看到的结果

- 一句话定位与核心内容支柱
- 最近样本表现和数据质量
- 自然内容规律
- 商业植入规律
- 语言、叙事和镜头习惯
- 创作禁区
- 结论对应的代表笔记
- Baseline 的采样范围、更新时间和置信度

### 异常路径

- 搜到多个同名账号：要求用户选择，不猜测。
- 少于 10 篇有效笔记或详情/正文完整度低于 80%：停止正式蒸馏并请求补采。
- 10–29 篇有效样本：允许生成探索性 Candidate，但置信度最高 0.65。
- 评论或口播不可用：不中断主流程，记录缺失维度。
- 旧 Baseline 已存在：成功 finalize 后生成新版本，不覆盖历史版本。

## 3. 上传 Brief 并建立项目

### 典型请求

> 根据这个品牌 Brief 写内容大纲。

### 流程

1. 导入原始 Brief，计算文件摘要并保存副本。
2. 提取文本，形成结构化 Brief。
3. 识别品牌、产品、平台、交付物、场景、受众、卖点、必须提、禁用词、节点和时长。
4. 区分“原文事实”“可靠推断”“仍需确认”。
5. 运行完备度和高风险缺口检查。
6. 只有缺口会实质改变路线或造成合规风险时，才向用户提问。
7. 创建 Project，并绑定使用的 Baseline 版本。
8. 生成 Brief 解析 HTML。

### 放行规则

- 缺少品牌、产品或交付物：必须先确认。
- 缺少非关键背景：允许带假设继续，并显式标注。
- 必须提、禁用词和合规限制不得由系统臆造。

## 4. 生成内容路线

### 流程

1. 读取结构化 Brief。
2. 读取项目绑定的 Baseline 快照，而不是隐式读取“最新版本”。
3. 检索相关历史定稿和已验证规律。
4. 默认生成 1 条最推荐路线；只有用户明确要求多个方向或指定数量时，才生成 2–3 条差异明确的路线。
5. 每条路线包含核心命题、场景、情绪、产品进入方式、适配证据、主要风险和 Brief 覆盖情况。
6. 推荐一条路线，但保留用户选择权。
7. 保存路线集合并生成 HTML。
8. 等待用户在对话中选择或反馈。

### 路线差异要求

生成多条路线时，路线之间不能只是标题或措辞不同，至少应在核心矛盾、叙事场景、产品角色或情绪路径中的两项存在差异。

## 5. 生成和修改大纲

### 流程

1. 用户选定路线。
2. 生成结构化大纲和可读 Markdown。
3. 检查 Brief 硬约束覆盖。
4. 检查与博主禁区的冲突。
5. 生成 `V1` HTML Preview。
6. 用户通过 Codex 对话提交反馈。
7. 保存原始反馈，并生成 `V2`。
8. 展示版本差异；重复直到用户决定将某一版提交品牌方。

### 每版大纲必须包含

- 当前版本和生成时间
- 绑定的 Brief 与 Baseline 版本
- 内容路线与一句话命题
- 选题名、暂定标题和 Hook；暂定标题只帮助理解路线，不作为品牌审核的最终发布标题
- 默认 7 段、可被 Brief 覆盖的分镜结构
- 每段一一对应的秒数、镜头、大致口播、花字和品牌露出
- 各段秒数相加得到的预计总时长
- “大致口播”供品牌理解内容，不等于博主最终逐字口播脚本
- Brief 覆盖矩阵
- 博主适配依据
- 风险和仍需确认项

## 6. 大纲品牌审核

助理通常需要把工具生成的大纲手工复制到品牌方提供的 Word、Excel 或在线模板。MVP 不要求自动填写任意品牌模板。

### 首次提交

1. 用户指定要提交的 Outline 版本。
2. 系统生成只包含对外交付内容的“纯净交付视图”，不展示内部证据、风险推理和 AI 备注。
3. 用户手工复制到品牌模板；如果复制时做了实质修改，先上传准备提交的实际文件。
4. 用户发出后告诉系统“已提交品牌方”。
5. 系统以品牌真正收到的内容创建不可修改的 `Brand Submission S1` 快照，并关联原 Outline 版本。
6. 如果事后发现登记内容与实际提交文件不一致，保留 S1 并创建校正记录，不能静默覆盖历史快照。

### 收到反馈

品牌反馈可以通过粘贴文字、上传批注文档、上传聊天截图或助理口述总结导入。

1. 保存反馈原件或原文。
2. 形成结构化 `Brand Feedback R1`，并关联它针对的 Submission。
3. 将每条意见标记为已理解、存在歧义或与博主人设冲突。
4. 修改大纲并创建新 Outline 版本。
5. 生成反馈处理矩阵：已处理、部分处理、未处理、待确认。
6. 用户再次提交时创建 `Submission S2`；循环直到品牌确认。

### 大纲确认

品牌确认后，系统将对应 Submission 锁定为 `Approved Outline`，保存确认时间、确认方式和助理备注。Approved Outline 不可被后续版本覆盖。

## 7. 生成并审核发布文案

大纲确认后，助理还需要向品牌方提供标题、正文和 Tags。系统将三者组织为 `Publication Copy`，但不生成博主最终口播脚本。

### 流程

1. 读取 Approved Outline、Brief 和 Creator Baseline。
2. 生成标题候选、正文和 Tags。
3. 检查 Brief 必提项、禁用词、活动信息和平台表达风险。
4. 生成发布文案 HTML Preview。
5. 用户反馈时创建新的 Publication Copy 版本。
6. 用户提交品牌时创建独立的 `Copy Submission C1` 快照。
7. 品牌反馈按与大纲相同的方式保存和处理。
8. 品牌确认后锁定为 `Approved Publication Copy`。

大纲审核和发布文案审核是两条独立版本链，不能用一个笼统的“品牌已过稿”状态覆盖。

## 8. 博主创作与拍摄（系统外）

Approved Outline 形成后，博主本人完成口播脚本、拍摄和实际内容表达。工具不生成最终口播脚本，也不要求助理维护博主创作过程中的每个内部版本。

项目的 Creator Production 轨道进入 `in_progress`。此时发布文案的品牌审核可以并行进行，两个轨道互不覆盖状态。

## 9. 上传最终发布内容并归档

### 典型请求

> 这是最终口播脚本和实际发布配文，帮我归档。

### 流程

1. 将文件绑定到已有 Project；如果无法唯一判断，要求用户确认项目。
2. 分别保存最终口播脚本和实际发布配文原件，并提取标准化文本。
3. 实际发布配文至少包含最终标题、正文和 Tags；允许一个文件同时承载三者。
4. 对比 Approved Outline 与最终口播脚本。
5. 对比 Approved Publication Copy 与实际发布标题、正文和 Tags。
6. 分别提取新增、删除、重排、弱化和强化的内容变化。
7. 将变化先解释为项目事实，并标记可能来源：品牌审核、博主创作、拍摄执行或无法判断。
8. 生成候选学习及支持证据；品牌反馈默认不进入 Creator Baseline。
9. 生成最终归档 HTML，更新项目索引和 Workbench 首页。
10. 等待用户决定是否接受、修改或拒绝候选学习。

最终归档可以先保存其中一种文件，但只有最终口播脚本和实际发布配文都齐全时，项目才标为 `archive_complete`。

### 候选学习状态

- `proposed`：系统提出，尚未 Review
- `accepted`：用户确认是可复用经验
- `rejected`：用户确认是个案或错误判断
- `promoted`：已进入稳定 Baseline
- `superseded`：被更新的规律替代

## 10. 更新 Baseline

Baseline 更新必须是显式操作，不是归档的副作用。

允许升级的依据至少满足一种：

- 用户直接确认该规律具有长期性
- 相同规律在多个独立项目中重复出现
- 规律得到发布表现数据支持

升级时必须：

1. 创建新 Baseline 版本。
2. 保留旧版本。
3. 记录来自哪些候选学习。
4. 重建相关 Workbench 页面。
5. 不 retroactively 改变历史 Project 绑定的 Baseline。

## 11. 对标分析（P0.5）

1. 用户提供 1–3 个账号。
2. 对每个账号建立独立、轻量的 Benchmark Snapshot。
3. 按账号自身时间窗口和内容中位数归一化。
4. 比较内容支柱、结构、评论需求和商业植入。
5. 输出机会项、可借鉴项和不适用项。
6. 对标结论不会自动进入本人 Baseline。
