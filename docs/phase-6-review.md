# 阶段 6 Review：真实项目端到端验收与 P0 收尾

状态：等待用户 Review

## 本阶段验收结论

P0 主闭环已经用一个真实、已发布的商业合作项目完成回放式端到端验收：

```text
真实账号公开数据 → Baseline / Playbook
真实品牌 Brief → 推荐路线 → 7 段策略分组 + Shot Rows 大纲
Outline Submission / Approval → 标题、正文、Tags → Copy Approval
最终口播原件 + 实际发布配文与截图 → 双轨差异 → 项目归档
差异与证据 → Learning Candidate → 人工确认 project_only
```

这次验收证明各对象、版本链、页面和归档能够贯通，但它是基于历史已发布项目的回放测试，不等同于助理在真实品牌协作期间从收到 Brief 开始的前向试用。

## 真实验收覆盖

1. 从公开主页和笔记数据建立本人 Baseline，并区分自然内容与商业合作内容。
2. 由用户人工补充商业合作名单、受众意图和表达例外，形成最终 Baseline 与创作 Playbook。
3. 导入真实 PDF Brief，保留原件并生成结构化约束。
4. 默认只生成一条推荐路线；在用户确认后选择品牌给定方向中的健身路线。
5. 生成满足不少于 120 秒要求的大纲，并将旧 scripts-agent 的格式升级为“7 段策略分组 + 逐镜头 Shot Rows”。
6. 创建真实的大纲提交快照与 Approval，再生成标题、正文和 Tags。
7. 根据用户反馈增加正文中的 Emoji 密度，形成并确认 Publication Copy V2。
8. 保存最终口播 DOCX、实际发布配文转写、发布截图和实际发布链接；原件以 SHA-256 标识且不可静默覆盖。
9. 分别生成 Approved Outline → 最终口播、Approved Copy → 实际发布配文的差异。
10. 生成三条候选学习，经用户确认后全部保留为 `project_only · accepted`，未修改 Creator Baseline。

## 回放测试的防泄漏边界

历史项目回放最大的风险是生成时提前看到最终答案。本阶段采用以下边界：

- 路线、大纲和发布文案生成上下文只读取项目绑定的 Baseline、Playbook、Brief 和已经批准的上游对象。
- 实际发布标题、正文、Tags 和最终口播只在归档阶段进入系统。
- 已知的历史最终配文不得作为 Publication Copy 的生成依据。
- 对最终成片的比较属于验收和复盘，不冒充对未来项目表现的预测。

因此，本次结果可以验证流程完整性与创作适配度，但不能单独证明首次生成命中率或品牌一次过稿率。

## 本阶段确认的产品决策

1. 完整画像同时保留自然内容和商业内容；自然内容用于创作本色，商业内容用于合作适配，两者不混算。
2. 小样本统计不只依赖简单均值，优先使用中位数、分组对比和去极值参考，避免单篇爆文主导判断。
3. 品牌强制硬广表达属于项目例外，不能因为一次合作写入博主默认语气。
4. 大纲维持“秒数、镜头、大致口播、花字、品牌露出”的可交付格式，同时增加策略分组与逐镜头双层结构。
5. 大纲确认后，标题、正文、Tags 使用独立审核链。
6. 最终口播由博主在系统外完成；工具负责归档和比较，不替博主写最终逐字稿。
7. 单项目变化默认只形成项目级候选经验；接受候选不等于升级长期 Baseline。
8. Workbench 继续保持本地、只读、可重建，结构化事实和原始附件保存在被 Git 忽略的 `.xhs-agent/`。

## 自动验证结果

- 自动测试：69 项通过。
- Workbench 重建：1 位博主、5 个 Baseline 页面、1 个项目、17 个页面。
- 构建警告：0。
- 自动化浏览器受安全策略限制，不能打开 `file://` 页面；页面结构、内部链接和静态资源由测试验证，视觉体验保留给用户人工 Review。
- Git 工作区中的真实业务数据、Token、原始附件与生成 HTML 均保持忽略，不进入本次 Review 文档。
- Workbench 可访问性与阅读优化已独立提交：跳到主要内容、中文认识状态、中文结论数量、紧凑首页分区和滚动目录状态。

## 仍未被本次测试证明的事项

1. 尚未用一个全新的、未发布 Brief 做前向盲测。
2. 尚未经历真实品牌方多轮反馈文件导入与订正往返；当前只验证了版本链和确认流程。
3. 样本仍是单一博主、单一项目，不能据此评价跨博主和跨品类稳定性。
4. 尚未回采发布后 7/30 天表现，因此候选经验没有数据验证。
5. 同类博主分析尚未进入产品，计划在阶段 7 实现。

这些限制不阻塞 P0 MVP 完成，但应该进入下一轮真实使用清单。

## 用户 Review 路径

请从 Workbench 首页依次查看：

1. 首页是否能快速区分博主档案与合作项目。
2. 博主 Playbook 是否足以让助理理解“像她”和“不像她”的边界。
3. 项目页是否能看清 Outline、Publication Copy、Creator Production、Publication 和 Archive 五条状态。
4. 发布文案页是否方便检查标题长度、正文、Emoji、Tags、Brief 覆盖和风险。
5. 最终归档页是否能找到原件、实际发布链接、双轨差异和三条项目级学习。
6. 页面在常用窗口宽度下是否仍然易读，左侧目录是否会正确跟随滚动位置。
