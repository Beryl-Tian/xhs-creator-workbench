# 小红书创作工作台：MVP 产品契约

状态：阶段 0 已通过

## 1. 产品定义

小红书创作工作台是一套面向博主助理的本地优先 Skill 产品。它把博主公开内容分析、品牌 Brief 转译、大纲生产、品牌审核、发布文案生产、最终内容归档和经验回灌组织成一个可追溯的工作闭环。

产品不是“模仿某个博主写作”的一次性生成器，也不是公开数据看板。它的核心资产是一个会随着真实定稿和发布结果逐步更新的博主创作模型。

## 2. 目标用户

### 主要用户

- 负责一位或少量博主的内容助理
- 能使用 Codex Desktop，但不应被要求理解命令行、JSON 或代码目录
- 日常任务包括分析账号、接收品牌 Brief、写大纲、协调修改和整理定稿

### 次要用户

- 博主本人
- 内容负责人或经纪人
- 需要复盘合作内容的数据运营

## 3. MVP 要解决的问题

1. 助理每次写稿都要重新回忆“这个博主是谁、什么表达像她”。
2. Brief 中的硬性要求容易遗漏，品牌要求和博主人设容易互相挤压。
3. 初稿、反馈和定稿散落在不同文件中，无法系统复用。
4. 单次定稿带来的经验没有进入下一次创作。
5. 竞品分析容易停留在绝对点赞量，无法回答“对我们有什么用”。

## 4. MVP 成功标准

MVP 必须让用户完成以下闭环：

1. 建立一个主博主的 Baseline。
2. 上传一个品牌 Brief 并得到结构化解析。
3. 基于 Brief、Baseline 和历史证据默认生成 1 条推荐路线；用户明确要求时生成 2–3 条。
4. 选择路线并生成可本地查看的 HTML 大纲 Preview。
5. 将某一版大纲标记为品牌提交快照，录入品牌意见并生成订正版。
6. 将品牌确认的大纲锁定为 `Approved Outline`。
7. 基于确认大纲生成标题、正文和 Tags，并单独完成品牌审核。
8. 博主在系统外完成口播脚本和拍摄后，上传最终口播脚本与实际发布配文。
9. 分别生成“确认大纲 → 最终口播脚本”和“确认发布文案 → 实际发布配文”的差异。
10. 将新经验保存为候选规律，而不是自动覆盖 Baseline。
11. 从 Workbench 首页进入博主画像、进行中项目和历史项目。

以下情况不算闭环完成：

- 只有 HTML，没有可重建 HTML 的结构化事实。
- 只有最终文件，没有 Brief、品牌提交版本、反馈和确认上下文。
- 定稿上传后立即、不经判断地改写博主长期画像。
- 大纲无法说明使用了哪些博主历史证据。

## 5. MVP 范围

### P0：主闭环

- 平台：仅小红书
- 博主：界面优先服务一个主博主；底层对象支持多个博主
- 公开数据：主页、笔记、互动数据、评论；口播转写可选
- Baseline：定位、内容支柱、自然内容规律、商业内容规律、表达风格、禁区、证据和置信度
- Brief：支持 Markdown、TXT、PDF、DOCX、XLSX 的文本提取
- 创作：内容路线、推荐理由、详细大纲、标题、正文、Tags、Brief 覆盖检查和版本管理
- 品牌审核：大纲与发布文案两类独立提交快照、反馈轮次和确认里程碑
- Review：静态 HTML 阅读，Codex 对话反馈；助理可手工复制到品牌模板
- 外部创作：博主本人写口播脚本和拍摄，不属于工具生成范围
- 归档：最终口播脚本、实际发布配文、原始文件、双轨差异、反馈和候选学习
- 展示：本地 Workbench 首页和项目页面

### P0.5：主闭环稳定后

- 1–3 个同类博主对标
- 内容支柱重合度与选题空白
- 对标账号相对自身 Baseline 的表现
- 可借鉴项与不适用项

### P1：数据增长闭环

- 录入发布链接
- 发布后 7/30 天数据回采
- 预测与实际表现对比
- 经验证的规律升级

## 6. 明确不做

- 不模拟登录、不注入 Cookie、不绕过平台访问控制
- 不在 MVP 中提供云端账户、多人实时协作或在线数据库
- 不自动发布小红书内容
- 不替博主生成最终口播脚本
- 不要求博主在工具内完成脚本创作或拍摄管理
- 不把每个定稿发布成新的独立 Skill
- 不承诺从公开互动数据推断曝光量或转化率
- 不用绝对点赞量直接判断不同体量账号的优劣
- 不把 AI 推断展示为已验证事实
- 不在未经用户确认时更新长期 Baseline

## 7. 产品原则

### 7.1 事实先于展示

JSON、Markdown 和原始附件是事实源；HTML 是可删除、可重建的投影。

### 7.2 证据先于结论

Baseline 中的重要结论必须能回到样本、定稿或人工确认。无法追溯的结论只能标为假设。

### 7.3 本人优先于对标

决策优先级固定为：

1. 品牌硬约束与平台合规要求
2. 博主人设不可变原则
3. 已验证的本人商业内容规律
4. 本人自然内容规律
5. 相关历史项目经验
6. 同类博主启发

### 7.4 候选学习而非即时学习

一次最终归档只能生成候选规律。品牌反馈默认沉淀为品牌、品类或项目经验，不能直接进入 Creator Baseline。来自最终口播脚本或实际发布配文的变化也要先判断来源；候选规律经人工确认、重复出现或发布数据验证后，才能成为稳定规律。

### 7.5 非 coder 优先

助理从 Workbench 和 Codex 对话完成任务，不需要手工编辑 JSON、不需要寻找运行日志、不需要启动 Review Server。

### 7.6 确定性任务交给脚本

文件读取、数据校验、统计、版本、差异、索引和 HTML 构建由脚本负责；内容理解和创作判断由 AI 负责。

## 8. MVP 运营指标

- 从收到 Brief 到可用大纲的时间
- 第一版大纲被品牌确认大纲保留的内容比例
- 平均修改轮数
- Brief 硬性要求遗漏率
- “不像博主本人”的反馈次数
- 历史证据被采用的比例
- 品牌反馈处理完成率
- 确认大纲到最终口播脚本的主要变化类型
- 确认发布文案到实际发布配文的主要变化类型
- 归档完整率

发布数据闭环上线后，再增加：

- 笔记表现相对账号同期中位数的倍率
- 路线推荐与实际表现的一致性
- 候选规律被验证或否决的比例

## 9. 阶段 0 暂定决策

- 在当前 `xhs-creator-workbench` 仓库开发新产品。
- `blogger-distiller` 与 `readNote-scripts-agent` 作为只读参考源；迁移时重新组织，不直接拼接目录。
- 产品暂用工作名“小红书创作工作台”，内部包名暂用 `xhs-creator-workbench`。
- MVP 先打通本人分析、Brief 到大纲、品牌审核、发布文案和最终归档；对标分析后置。
- Workbench 只承载人类可见结果，运行状态放在 `.xhs-agent/`。
